# 架构分析的外部核验与审查方法

本轮将 Godot 官方示例的一小部分源码作为外部作者样本，固定到提交 `b761b4cd5718a7118f2c95eb55f181d0a5f004f1`。本助手先读取源码、梳理预期引用并冻结标签，再运行现有分析器；没有为了提高本轮分数调整解析器。

[首次结果](external-analysis-v07.json)：8 个源码文件均与标签匹配，7 条显式资源边命中、误报 0、漏报 0。标签和源码 hash 见 [清单](../evals/analysis-external/manifest.json) 与 [标签](../evals/analysis-external/labels.json)。来源是 [Godot 官方 demo 仓库](https://github.com/godotengine/godot-demo-projects/tree/b761b4cd5718a7118f2c95eb55f181d0a5f004f1)，所取代码保留 [MIT 许可](../evals/analysis-external/LICENSE)。

## 如何解读

这是外部作者源码、在首轮评估前冻结标签的固定样本；标签仍由同一助手整理，不是独立人类盲评。样本小且有选择，只评 load/preload/extends/ext_resource 的边标识，不评整个游戏架构、资源实际可导入性或所有动态依赖。目标资源没有全部下载，因此缺失标记不纳入此边识别分数。

两个明确的盲点保留在结果内：通过 FileAccess 读取运行时对话文件，以及按用户选择用格式专属 API 加载图像/音频/模型/字体。源码 UID 不完整时仍保留 unknown。以后若拿这组结果改进解析器，应把它归为回归集，再准备新的未见样本。

复现，不联网：

```text
python tools/evaluate_external_analysis.py --output new-external-results.json
```

工具先核验源文件与标签的冻结 hash，内容漂移会失败；不会重写标签。Git 检出的 CRLF/LF 差异按文本规范化处理。

## 对真实架构建议进行人工核验

使用者在自己的私有记录中逐项填写，不需要上传源码：

| 项 | 需要回答的问题 | 当前证据与状态 |
|---|---|---|
| 缺失资源 | 是可执行引用、备用路径、占位文字，还是预期下载内容？ | 先核对调用点、UID 和目标实际存在性；不要直接删除 |
| 动态路径 | 值来自什么配置/存档/用户输入？实际运行使用了哪些值？ | 保留未知，补运行记录；不能把没有静态边写成没有依赖 |
| 状态写入 | 是否为同一实例、同一生命周期？局部变量是否遮蔽？ | 赋值线索不证明竞争写者；需追装配和类型 |
| 循环依赖 | 是否实际阻碍初始化、销毁、测试或下一次扩展？ | 回到真实任务验证，不按环数量自动重构 |
| 改进价值 | 修复后，同一缺陷是否消失，后续改动是否减少？ | 要有前后产物、相同验收与独立评审；本轮人类评审待补 |

本轮没有把助手自检改称人类评审，也没有因为这个小集全部匹配而宣称全工程准确。

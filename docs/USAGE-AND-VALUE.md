# 如何使用、实际价值与发布判断

评估日期：2026-11-11。本次评估对象是 GameDev Workbench 工具项目，不是试图公开用户的私有游戏。

## 当前真正具备的功能

| 层面 | 能做什么 | 不能据此声称什么 |
|---|---|---|
| 技能与方法 | 按任务加载架构、原生 UI、功能、效果、验证、创意、剧情、美术资产、资源研究与导航流程 | 不会让模型自动具备新的视觉品味或专业判断正确性 |
| 知识导引 | 按制作阶段和问题查学习路径、来源、许可与限制 | 不是完整教材、实时网络搜索引擎或素材版权担保 |
| 离线工具 | search、inspect、route、brief、doctor、validate、安装计划与复制；analyze-project 收集入口、引用与状态写入线索 | 不会自动接管编辑器；文本分析不是完整语义或所有权证明 |
| 内置执行 | verify-godot 与 check-ui-effects 在临时副本运行自有样例；布局/焦点助手可显式接入自己的夹具 | 不是任意 Godot 项目的自动测试器，也未连接第三方 MCP |
| 示例与评估 | 响应布局、信号接线、可重播效果、新菜单五视口/两字号/四十帧证据，以及独立配对修改与共同验收 | 一个脉冲环和一个修复任务不足以证明复杂特效、所有游戏 UI 或普遍提效 |
| 发布材料 | 自有许可、第三方声明、贡献规则、可安装技能、可解压项目与校验和、CI 与公开发行入口 | 预览版本不等于经过独立用户长期试用；各平台状态看当前 CI |

## 最简单的用法

在支持此技能的代理会话中，写出目标、项目与约束即可。例如：

```text
$gamedev-workbench 审查当前项目的架构，先给状态所有权、依赖和风险，不改代码。
$gamedev-workbench 制作当前游戏的暂停菜单，沿用现有主题，验证键盘返回和焦点恢复。
$gamedev-workbench 实现一个可重复触发的命中效果，先做隔离预览，再接正式入口并检查清理。
$gamedev-workbench 对三个机制方向做成本与风险比较，给我最小可玩验证方案。
```

如果希望执行修复，明确允许改哪些内容，例如“实现前两项问题并运行相关回归”。若希望推送、上传素材或连接云服务，需要明确包含这些外部动作；技能名称本身不提供额外授权。

无需使用命令行也能阅读工作流与模板。工具使用者可从项目根目录执行：

```text
python tools/gdw.py brief "游戏菜单焦点与布局" --engine godot --project "你的项目路径"
python tools/gdw.py search "架构"
python tools/gdw.py inspect S04
python tools/gdw.py analyze-project "你的Godot项目路径" --output "工程分析.json"
python tools/gdw.py verify-godot --engine "官方引擎路径" --scratch "可写临时目录" --output "结果.json"
python tools/gdw.py check-ui-effects --engine "官方引擎路径" --scratch "可写临时目录" --output-dir "新证据目录" --graphical
```

brief 的路径相对技能根目录；先读项目规则，再打开被选工作流和模板。引擎实际版本由 doctor/verify-godot 核验，project.godot 的 minor 标记不证明 patch。

## 是否有实际提升

可以确认的改善是：工作步骤、项目约束、验收与来源被明确组织；同一任务的准备过程更容易复用；失败和未验证部分更容易暴露。本轮修正了英文 build 中 ui 被误匹配的问题，固定的关键词微型回归由 8/12 到 12/12。该数字只描述这个小集合上的路由逻辑修复，不代表任务完成率或模型能力提升。

新增工具把手工收集工程线索、布局/焦点检查和效果时间采样变成可复用执行过程。新菜单完成五视口、两字号、四十帧和一百二十一项检查，并另做窗口 OS 自动键鼠交互；这证明包内工具可执行，不能直接背书用户游戏。另曾在用户真实项目中用此工作流发现并修复存储失败传播和遭遇重入问题；那些修复没有无技能对照，不能归因于技能本身。

仍待证明：是否减少返工、是否提高架构判断质量、是否降低 token/费用、是否比现有游戏技能库更好。主观认为流程清晰，不足以支持这些声称。

## 如何真正验证提效

建立一组固定任务，覆盖架构、原生 UI、效果与故障修复，使用原创小仓库与预先留出的缺陷。先冻结任务，再分别用同一模型、工具、预算与初始状态执行“无本技能”和“有本技能”；每次在干净副本运行，禁止把先前结论泄漏给后一组。

记录：功能/行为通过、未授权改动、回归、人工修改量、有效耗时、模型成本与证据完整性。将输出匿名后按统一标准人工评审；创意方向另安排真实玩家观察。保留失败与无提升案例，结果按任务分组，避免一个总分掩盖 UI 或效果退步。

已执行第一轮独立小项目修复预试验：两组共同验收均 15/15、验收后返工均为 0；A 工作记录 261.846 秒，B 为 343.781 秒。环境补充时机不对称，耗时包含工具等待，精确后端 ID 与费用未暴露；不能因单次结果推断一般效果。本轮 B 使用 0.2 技能，未评估新增 0.3 工具。详见 [完整对照报告](PAIRED-EVALUATION.md) 与 [复验夹具](../evals/paired/README.md)。

## 发布有没有可行性

有实验版发布的可行性。当前最合适的定位是“面向小团队、重视项目约束和验收的中文游戏开发工作流与离线工具包”。暂不以“全面自动开发游戏”“所有引擎生产可用”或“显著提效”宣传。

现成项目已覆盖大量领域：[awesome-gamedev-agent-skills](https://github.com/gamedev-skills/awesome-gamedev-agent-skills) 提供多引擎任务路由与专业技能，[Scenario skills](https://github.com/scenario-labs/skills) 提供大量专业工作流和工具。因此单纯加网址、角色提示或条目数量很难形成独特价值。这个项目更值得做深的方向是：把真实任务连到项目规则、原生产物、执行工具和复现证据，并公开其适用条件和失败情况。这是本次评估判断，不是竞品全面审计。

采用 [Agent Skills 格式](https://agentskills.io/specification)便于便携分发；格式通用不等于每个代理客户端行为相同。首发应邀请不同项目的少量外部使用者试用，再决定是否投入更大的工具平台。

公开版本的维护者为仓库所属账号，支持平台和条目状态见各自证据与元数据。原始游戏审查、实际日志中的本机路径和私有游戏源码不进入公开示例；只发布原创示例和脱敏证据。入口见 [GitHub](https://github.com/kaltsit2077-dev/gamedev-workbench)，具体版本以 Releases 和提交记录为准。

## 下一步优先做什么

| 优先级 | 能力 | 为什么值得做 | 验收方式 |
|---|---|---|---|
| 首先 | 扩展真实任务与代理对照 | 首轮完成但未证明额外价值；加入 0.3 工具处理组 | 多任务重复、预先冻结完整验收、匿名盲评、实际计费记录 |
| 高 | 只读分析的人工核验 | 文本工具已完成，源 UID/有限常量和标注回归已补，继续独立核验运行时动态引用与误报/漏报 | 对照人工事实，未知不推断，版本化回归 |
| 高 | 将 UI/效果助手接入实际场景 | 原生嵌套菜单与分层效果已测，继续实体硬件及实际游戏集成 | 明确夹具、多尺寸、物理键盘/手柄、时间采样、重复与清理 |
| 中 | 任务配置与回归执行适配 | 按项目声明调用测试，统一证据格式 | 执行前可审查计划，失败退出码与超时真实可见 |
| 中 | 一个经过同任务比较的编辑器 MCP | 只有实际操作瓶颈成立时才接入 | 读取/编辑/撤回/运行/停止，同一小仓库比较 |
| 中 | 来源更新与兼容性维护 | 保持资料可信，避免旧版本误导 | 版本与许可变化人工审阅，不直接自动安装升级 |
| 后续 | Unity/Unreal 执行案例 | 扩大真正可验证的引擎范围 | 各自官方环境运行证据，不能借 Godot 结果背书 |
| 后续 | 叙事、音频、经济与关卡专用工具 | 全面地图逐步变成实际能力 | 可试玩分支、音频事件/混音、数值模型与关卡原型 |

暂不优先增加向量数据库、庞大网站或统一修改所有引擎的 MCP；出现真实检索规模、协作或多后端重复成本后再建设。

0.5 已补有限叙事检查、整数经济模拟、资产依赖预检及编辑器案例入口，格式见技能内工具配方。新增两轮设置事务对照四组都通过，未观察到验收后返工改善；本轮没有实际账单数据。实体输入、Unity/Unreal 真实运行与性能仍单列未验证。


0.7 已增加创作工作区、离线工作页、项目声明测试及共同适配报告；上面的优先级表保留早期判断，当前顺序以 [ROADMAP](ROADMAP.md) 为准。新增外部源码核验与预设缺陷检出记录见 [验证报告](VALIDATION.md)。新的独立模型/人类评审/实际费用仍未采集，不能以工具检出试验替代。

# 定位：辅助 AI 完成小型和中型游戏开发

状态：核心以可安装 skill 交付，工具按任务使用。可视化是补充。以 [能力矩阵](CAPABILITIES.md) 和 [验证记录](VALIDATION.md) 区分可用方法、运行工具和未验证目标。

## 具体作用

帮助已有 AI 助手理解整个项目，再完成局部任务；减少脱离工程上下文的代码、重复状态、遗漏场景接线和无法复现的修复。面向个人和小团队，也包括已有较复杂工程。中型项目适用是设计目标，尚未用长期团队数据证明效果。

| 工作 | 技能要求 AI 做什么 | 需要验证的结果 |
|---|---|---|
| 项目与代码架构 | 读规则/决策，追踪真实入口、数据流、状态所有者和生命周期；按变化压力选择接缝与迁移 | 建议关联具体改动风险；迁移后消费者与回归仍工作 |
| 规划与持续开发 | 结合当前工程把目标拆成可运行步骤，明确依赖、范围、责任和验收；恢复时核对真实工作树 | 换任务或换人后能继续，已有约定不丢失，计划会随反馈调整 |
| 功能实现 | 同时完成代码、资源/数据、场景装配与用户反馈；处理失败、取消、重入和清理 | 用户可从真实入口使用功能，相关旧功能不回退 |
| 多人 Git 协作 | 核对分支、未提交改动、资源元数据和所有权；按双方意图解冲突，在集成树上测试 | 他人功能保留，源文件与 UID/.meta 成对，合并后行为正确 |
| Bug 修复 | 固定复现、区分事实与假设、定位根因，先证明失败，再修复并测相关消费者 | 旧实现能复现失败，修复通过，未靠吞错或删断言掩盖 |
| UI、效果和创意 | 保持项目风格；需要探索时比较玩法、信息组织、交互和视觉语法的实质差别；交付原生可编辑产物 | 与整体工程一致，有实际运行/画面/输入证据；好玩与审美另需试玩 |

流程深度随改动影响调整。小修直接沿现有契约实现；跨系统、存档迁移、共享资源或多人任务才需要更明确的契约和拆分。不以文档数量、目录层数或强制套架构衡量质量。

## 交付结构

- **Skill 为核心**：短入口按任务加载规划、架构、实现、调试、协作、UI/效果、创意与验证方法。复用项目已有 ADR、票据与交接记录。
- **离线工具辅助取证**：架构文本分析、Git 只读检查、显式项目测试、叙事/经济/资产专项检查。工具不替代源码审查和真实引擎验收。
- **知识库可独立**：长篇导引、书目、来源和许可适合另一个版本化项目。当前尚未迁移；先确保稳定的资源引用、离线可用与旧入口兼容。
- **插件和 GUI 按实际缺口增加**：先验证具体宿主和编辑器能力，再包装执行服务；界面用于查看差异、证据或操作难以在对话中完成的任务。当前没有独立模型平台或已验证的多宿主插件。

## 之后的顺序

1. 先在真实游戏开发任务中持续使用当前技能，覆盖架构改动、功能接线、修复与多人集成，记录失败、返工和遗漏；以问题决定下一项工具。
2. 扩大冻结的独立对照任务，加入未见工程和人类审查；记录全流程耗时及有来源的真实费用。通过检查不等于比无技能更好。
3. 增加跨引擎的真实执行。已有 Godot 原生记录，Unity/Unreal 案例与入口仍缺本机编辑器验证；不借别的后端通过背书。
4. 确有重复编辑器操作/状态读取缺口时再验证 MCP，比较其效果与成本。宿主兼容性逐项实测，模型 API 兼容不代表技能、权限、GUI 全部兼容。
5. 知识库分离与可视化包装在核心工作有效后推进，保持纯对话使用路径可用。

## 是否有效的判断

看实际产物：职责与状态是否清楚，需求是否接入现有工程，冲突是否保留双方行为，故障是否可复现且修复，相关回归是否在最终树上跑过。质量、返工、时间和费用分开报告；没有账单就保留未知。独立同模型任务、长期真实使用与人工评审共同补证，不以一个成功夹具推广为全面提升。

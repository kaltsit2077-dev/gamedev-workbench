# 产品方向修订：面向新手的 AI 游戏创作领航插件

状态：产品设计提案。依据用户最新说明修订定位；此处的目标体验不代表 0.7 已实现。现有可运行能力仍以 VALIDATION.md 为准。

## 首要目的

配合已有 AI 助手，让新手开发者更有创造性、更连贯、更可控地完成游戏。主线是创意、全局规划、工程契约、实现与反馈；分析器、测试和知识检索服务于这条主线。独立模型平台、单纯资料聚合与测试仪表盘不作为产品中心。

一句话：帮助使用者和 AI 一起确定“想做什么体验、有哪些不同做法、这次先做什么、为什么这样做、怎样接回整个游戏”。

## 产品与知识分开

建议两个可独立发布的项目，名称暂定，尚未创建新的远端仓库：

| 项目 | 内容 | 使用者为什么需要 |
|---|---|---|
| GameDev Workbench 创作插件 | 按目标工作的技能、项目记忆、创意探索、工程契约、任务状态、执行与交互界面 | 日常配合 AI 做游戏 |
| GameDev Atlas 知识项目 | 学习路径、资料来源、风格案例、引擎文档索引、许可与版本、外部工具评述 | 查阅、学习或给各种助手按需取材 |

插件保留决定行为所必需的短流程和契约；长篇资料、书目与大规模来源目录适合独立。已有制作方法不能因“知识库分离”全部搬走，否则技能会失去操作指导。

插件不依赖知识项目在线可用才能工作。按任务读取固定版本的选定资料；缓存可离线，记录来源和许可。知识更新不直接改变已确认的游戏风格与工程规则。

迁移应先建立资源包版本与读取接口，再搬来源目录/学习导引，更新调用方和许可、验证旧入口后再移除副本。当前不删除 catalog/references，不破坏既有安装；独立仓库发布另作明确迁移交付。

## 从新手的一次使用开始

### 带着想法进来

第一屏用“我有一个游戏想法”“继续已有项目”“我想改善某个界面/效果”三个实际目标开场。引擎、目录、测试工具放在与任务有关的时候出现。

例如：“我想做一个修飞船、送货、遇见不同旅客的小型游戏，但不确定怎么开始。”先帮助明确玩家动作、希望产生的感受、自己的资源与时间；已有答案就沿用，只问当前真正影响选择的问题。

### 看见不同方向

在方向尚未确定时给少量实质不同的提案，每个包含玩法重心、信息布局/交互、画面与反馈的可看或可玩片段、实现成本和最危险的假设。

同一委托/航线界面可以探索：

- 维修手册：纸面网格、工单与印章，读写和排程为主。
- 模拟座舱：空间雷达、仪表和实体键感，观察与操作反馈为主。
- 太空邮局：包裹、柜台与航线卡，整理和交付为主。

这是说明“差异要落到布局、交互与信息表达”的例子，不是以后每款游戏必须从这三种模板选。用户已有确定风格时优先保持一致，只有请求探索时才扩大差异。

### 选定一个可玩的起点

先给全局粗地图，再细化最近的可玩切片。页面说明“先做哪一小段、为什么先做、完成后能玩到什么、暂时舍弃什么”。不要要求新手先填写大量术语表或阅读整本设计文档。

设计可以回退，探索原型保留为探索；选择方向不意味着所有代码和美术都已批准。对低影响日常编辑沿既有授权推进，跨模块/风格根本变化时解释影响范围，不机械地每一步都停下来确认。

### AI 在整体工程中继续做

每次任务带上最少必要的项目上下文：体验支柱、已选风格、当前切片、有关模块/接口/状态所有者、既有约束、上次未完成项。AI 先找现有实现与接缝，再增加代码。新增一套并行管理器、重复数据源或复制逻辑，需要有具体变化压力与替代方案依据。

修改需求时给易懂的影响说明，如“新增一个设置项会影响状态、存档和菜单显示”；区分助手推断与源码/运行证据。不声称静态扫描能证明整个架构良好，也不把维护文档数量当工程质量。

### 看到结果，知道下一步

优先展示可操作的游戏片段、原生界面、效果重播和修改差异。检查结果作为辅助，清楚说明已经运行和还需试玩的部分。完成一段后更新少量项目事实和下一步，下一次对话可继续。

## 三个核心体验

### 创意探索

从玩家体验与参考出发，拆解可借鉴的机制、布局、视觉语法、节奏和反馈。记录参考 URL、所借鉴的层次和许可，不把参考图片直接当可用游戏素材。根据宿主工具能力调用绘画/建模/设计工具；没有工具时明确交付规格或可编辑程序化原型的范围。

防止结果趋同的办法：方向比较需体现信息架构、交互、造型/材质、排版、动效等实质选择；记录不喜欢的常见做法；保留已试过和淘汰的方向及原因。选定后形成当前项目的风格约定，后续实现沿用。跨项目应有差异，同一项目应保持一致。

### 项目领航

把创意变成可玩的最小切片，再变成可持续迭代的整体计划。既能新建游戏，也能接手旧工程。任务连接到玩家价值、所属系统与验收；变化时调整计划，不靠无止境追加待办制造进度。

### 工程连续性

用职责、状态归属、数据流、生命周期、接口与回归约束 AI 的局部修改。根据改动规模选择记录深度：文字修正不需要完整架构评审；跨系统变化需要契约和迁移顺序。插件帮助保持连续性，无法保证自动杜绝坏架构。

## GUI 应怎样呈现

中心是当前要做的选择或游戏预览；侧边是“当前目标/已决定/下一步”，展开后才出现工程细节。主要动作应是“比较方向”“解释为什么”“试做一小段”“查看改变影响”“继续上次进度”。资料按当下问题引用，不以大目录首页开场。

可见交互必须有消费方：设计演示只改变演示状态；接入真实宿主后才声称执行了模型/文件/引擎操作。按钮、状态和结果要让新手知道接下来发生什么，不能用动画掩盖等待和失败。丰富视觉优先用在游戏创意比较和反馈预览。

## 实现形态与适配边界

先把核心做成自包含、可移植的技能；再用插件打包相关技能和有实际用途的工具服务，按宿主能力增加交互界面。GUI 不能仅靠 SKILL.md 获得；工具调用、持久状态、界面呈现与文件权限需要各自适配。

OpenAI 官方文档确认插件可组合技能、MCP 和可选 UI，但个别能力受使用端限制。通用工具在没有 GUI 的端也应能通过对话工作。DeepSeek Harness 等作为候选宿主分别核验，不能因模型 API 或某项协议兼容就宣称插件 GUI/权限/恢复全部兼容。

资料：[OpenAI 插件架构](https://developers.openai.com/plugins/concepts/plugins)、[可选 UI 与 MCP Apps](https://developers.openai.com/plugins/build/chatgpt-ui)。本轮没有安装宿主插件或验证 DeepSeek Harness 的 GUI。

## 优先制作的真实闭环

先选一个已有 Godot 工程任务，覆盖“创意/风格发散 → 用户选择 → 全局位置与工程契约 → 可操作 UI/效果切片 → 运行/试玩 → 继续迭代”。让一个初学者在助手帮助下完成它，记录困惑、风格是否确有差别、修改是否接回既有系统、再次继续时是否丢失关键决定。

接着才扩大引擎与宿主范围。已有分析、项目测试、原生案例和证据工具继续复用，放到创作旅程的合适位置。

## 验收重点的变化

- 创造性：同一目标能否产生有意义的不同选择，且使用者能解释偏好？不能只换色或换一张背景。
- 新手可用性：能否理解为什么做这一步、选出一个方向、得到可玩的最近目标，并在卡住时知道怎么继续？
- 工程连续性：需求改变后是否复用已有契约、避免第二真值源，能否解释状态归属并完成相关回归？
- 制作完整性：从规格到代码/场景/资产/输入/试玩，哪些已完成、哪些未做，是否清楚？
- 长期有效性：换对话或继续上次任务是否保留关键决定？独立用户是否减少迷路与返工？

这些需要真实使用和评审，不能用生成文档数、自动检查数或漂亮演示单独证明。

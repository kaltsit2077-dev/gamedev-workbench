# 项目规划与连续开发

用于新功能跨多个系统、接手现有游戏、规划迭代或多人交接。先读取项目现有设计、代码导航、决策与回归入口；已有载体能承载的事实不另建副本。

## 先决定这次需要多少规划

- 局部修正：沿现有契约直接修改和验证，简述影响。
- 跨模块功能：明确玩家行为、状态所有者、接口、装配/销毁、数据/场景/存档影响及验证入口，再拆可运行步骤。
- 跨迭代或多人工作：在上述基础上记录依赖顺序、负责边界、可并行部分、容易争改的共享文件、集成时机和回退点。

规模按变化影响判断，不按文件数强行区分“小型/中型”。小型项目也可能有高风险存档改动；中型项目的文字修正仍走轻流程。

## 从整体到本次交付

1. 确认当前版本能做什么、用户希望改变什么、哪些决定已确定。体验/创意仍不明确时用 design；已有方向时保持其风格与规则。
2. 追踪一条真实使用路径，列出受影响系统及现有负责人：玩法/数据、表现/UI、输入、持久化、资源、装配与生命周期。无证据的所有权标记未知并核对。
3. 将目标拆成每步可运行、可集成的切片，列各自输入、输出、依赖、验证与停止条件。优先复用已有接缝，不为将来可能的需求预建框架。
4. 对多人改动划分接口与文件边界；共享场景、资源目录、全局单例、配置和 UID 迁移安排明确集成人。个人分支上的测试不能代替合并后的测试。
5. 每个切片用实际 diff、相关回归及必要的原生画面/操作验收；更新项目已有进度载体。交接只保留会改变后续决策的事实。

继续上次任务时，以当前分支、工作树和已落盘产物校验交接记录；过期计划不当作现状。需求改变时说明哪些决定、接口和任务失效，避免只往清单末尾追加。

## 应留下的最少信息

目标与不做项；当前基线；受影响契约；当前切片与后续依赖；负责人/共享文件；验证入口及已知失败；未完成项和下一步。可直接写进已有票据或 PR；需要新载体时使用 [交接模板](../../templates/handoff.md)。

## 独立验收与恢复

切片应从一个真实玩家入口走到可观察结果，包含必需的状态、资源/场景接线和验收；按这个结果拆任务，避免先写完所有数据类再补所有 UI 才第一次运行。并行资格同时看接口、状态所有者和共享资源，不能只看文件是否不同。恢复任务只带相关决定的指向、未满足的验收和当前变更；对照实际分支/文件复核，不用旧“完成”标记代替证据。来源与取舍见 [上游参考](../upstream-patterns.md)。

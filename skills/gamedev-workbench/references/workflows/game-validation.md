# 调试与验证

输入：现象、期望、可复现步骤、引擎/后端/平台、日志与最近改动。

1. 分类为解析/编译、装配、行为、渲染、性能或玩家体验问题。先记录最小复现和原始证据。
2. 提出可以被推翻的原因假设，每次改变一个相关变量。无法复现时明确缺少的输入，不编造原因。
3. 功能用行为断言；UI 用交互与多尺寸；效果用时间序列和清理；性能用相同场景的前后测量；玩法用真人观察。
4. 对照既有失败基线；把新失败归入实现、设计/契约或环境。不要为了测试通过反向扭曲正式语义。
5. 报告已验证维度、命令/工具、版本、产物、退出码、未测项和复测入口。

交付：templates/evidence.md，必要的最小复现与修复。来源：E02、E05、A05、A06。

禁止把“没有错误日志”写成所有路径通过。无显示设备、无引擎或错误版本应记录 blocked/unverified，不判成功。


## 对照与实际测量

工程工具与技能提效分开评价。完整项目的 `tools/paired_eval.py` 可准备一致输入并统一验收产物；模型需由宿主或使用者以相同配置独立运行。不可取得 token/费用时记 null，耗时须说明计量边界。单个任务两组都通过，不应声称通过率提高。

完整项目的 tools/repeated_eval.py 提供预先冻结完整验收的设置事务任务。技能内 summarize-evals 只汇总有来源的记录，估算不能进入实际费用。typed engine events、OS automation 和实体输入分别登记，配方见 ../tool-recipes.md。

针对状态切换或异步行为，加入“源状态已退出/场景已销毁后旧任务才完成”的反例，检查旧结果没有继续触发动作或写新状态。原生场景 runner、参数化输入和孤儿节点检测可按缺口选用；框架 README 的能力声明仍不是本项目实测。上游入口与兼容限制见 [参考](../upstream-patterns.md)。

# 工程架构

输入：项目目标、引擎/语言/渲染管线、代码与场景导航、当前困难、下一次预计变化。已有仓库先读取 AGENTS.md 和任务相关 ADR；目录名不能证明运行时依赖。

1. 从一个真实入口追踪装配、更新、事件、持久化和销毁；记录文件与唯一符号，不使用易漂移的活行号。
2. 画出模块与依赖方向；每项重要状态列出声明者、写者、读者、有效期。区分数据定义、实例状态、视图和服务。
3. 复现当前问题，找出多写者、循环依赖、隐式初始化、跨场景残留或资源共享污染的实际证据。
4. 比较保持现状、局部接缝、边界调整三个可行方案；按下一次改动成本、测试、性能和迁移成本选择。框架、ECS、事件总线均须有问题依据。
5. 给出接口输入/输出、失败行为、时序、唯一所有者和清理责任。把迁移拆成仍可运行的步骤。
6. 用已有回归证明行为；涉及数据资源时同步断言。对照迁移前后的具体问题，不把目录重排计为架构改善。

交付：现状依赖图、状态所有权表、决策与反例、迁移/回退步骤、实际验证记录。采用 templates/architecture.md。来源查 catalog：E01、K11、S04。

验收问题：下一次新增能力需要改哪些地方？谁推进时钟和写位置？场景离开后谁释放订阅？缺失依赖是明确失败还是静默半初始化？


## Godot 只读线索工具

可用 `python scripts/workbench.py analyze-project "项目路径" --output "报告.json"` 收集入口、autoload、资源引用、循环和状态赋值线索。默认排除隐藏/缓存、插件与测试；报告自带扫描范围、快照时间和源码指纹。它不解析完整语义，不能把同名属性合并成唯一状态或把动态引用当成没有依赖。先核对关键链路，再写架构判断。报告可能透露工程结构，公开前脱敏。

源 UID/有限常量、遮蔽与快照比较的范围见 ../tool-recipes.md。遇到未知/冲突先保留证据，不把文本索引写成引擎已确认依赖。

# Bug 定位与修复

输入是用户观察到的行为、期望和可用工程。用户不必先给根因。先按项目规则保护当前工作树与其他人的改动，再定位相关代码、数据、场景和近期变更。

1. **复现而后归因。** 固定触发路径、初始状态、引擎/平台和失败基线。先复现原问题；不能复现时说明缺少的条件，用可验证的下一步收集证据，不直接写“已修复”。
2. **区分失败层次。** 解析、资源/UID、场景装配、行为、时序、输入、渲染、性能或存档。日志是线索，不以没有报错认定行为正确。
3. **检验具体假设。** 从入口追到状态写者、信号/订阅、计时器/异步回调、实例资源与数据声明。一次改变一个相关因素；必要时比较最近变更或在独立副本缩小范围。
4. **修正根因与所有入口。** 若问题是状态顺序、订阅残留、重复调用或持久化失败，修契约对应的路径，并检查其他消费者。不要靠多加一套状态、吞掉异常、延迟一帧或特判型号来掩盖原因；有必要的保护必须说明它维护什么不变量。
5. **先失败后通过。** 对值得回归的缺陷，在原始实现确认断言会失败，修后用同一验收重跑。覆盖与根因相关的边界，如失败写入后状态是否提交、重入、取消、离场、暂停与重复触发；不为低影响编辑编写镜像实现的测试。
6. **判断修复层级。** 依照已有设计实现后问题依旧，回到设计/契约；仅实现偏离契约，局部修正。现有回归与正式行为冲突时，先读项目决策确认哪方过期。
7. **验证集成结果。** 跑受影响域回归与必要的原生场景。修数据/资源时同步断言与引用，保留已知环境失败，不能用模拟测试替代引擎行为。

交付根因、实际改动、原失败与修后结果、相关回归、尚未复现/未验证部分。必要时使用 [缺陷记录](../../templates/bugfix.md)。没有通用“改好一次即全工程无 bug”的结论。

# 多人 Git 协作与版本集成

适用于多人/多代理改同一工程、分支集成、冲突处理、提交审查和交接。项目自己的分支、推送、锁文件、资产和回退纪律优先；不另强推 Git Flow、trunk-based 或特定提交节奏。

## 开始前

核对当前分支/HEAD、已暂存/未暂存/未跟踪文件、正在进行的合并/变基、上游与本地基准。区分自己的改动、合作者改动与未知归属。记录要改的接口和共享文件；需要隔离时沿项目规则使用工作树或独立副本。

可用 `python scripts/workbench.py review-git "项目目录" --base "本地基准引用" --output "新报告.json"` 收集只读证据。工具不会 fetch，远端引用可能过期；没有上游或对象读取失败时保留未知。报告是协作检查线索，不判断该采用哪一边的设计。

## 分工与提交

- 尽量按模块/完整切片拆分，每项明确输入/输出与集成人。单纯分给不同目录仍可能争写同一全局状态或资源。
- 对共享场景、资源列表、autoload、导出/项目配置、生成文件与大二进制明确所有权和集成时机；沿项目既有锁/LFS 策略，不自动迁移历史或安装大文件工具。
- 与正式类契约联动的数据、断言、UID/旁车和引用作为一个可验证改动集。改名或移动时检查引用与大小写，不只移动当前平台能找到的文件。
- 提交前审查暂存 diff，排除无关/他人改动与本地缓存，运行相关回归，按项目要求检查仓库健康。提交信息描述实际结果；不自动扩大既有推送授权。

## 合并与冲突

先读冲突两侧与公共基线的意图、约束和新增行为，再决定结果。项目已经裁决某域优先级时执行裁决，同时核验能否保留正交改动。

删除冲突标记只是文本收尾。需要同时保留双方功能时，明确合并接口/数据，并用共同验收确认两边行为都在。不能一律取 ours/theirs，也不能凭“解析通过”判定场景接线、存档和 UI 都正确。解决 `.tscn/.tres/.uid/.meta` 等冲突时核对关联文件、对象引用及导入结果。

合并后的实际树上跑回归；与合并前失败基线区分。若无法判断语义归属，具体指出相冲突的行为和需要的决定，保持可恢复状态。

## 恢复与交接

出现问题先保存当前状态证据与自己改动范围，沿项目已授权的撤回方式恢复；不把 `reset --hard`、强推、清理未跟踪文件、stash 或仓库对象整理当默认修复。需要撤回自己的提交时检查后续依赖与他人变更。

交接记录当前提交/分支、改动归属、基准是否新鲜、未解决冲突/风险、实际回归与下一步。交接文本不代替真实工作树检查。

Git 接口参考：[status](https://git-scm.com/docs/git-status)、[diff](https://git-scm.com/docs/git-diff)、[ls-files](https://git-scm.com/docs/git-ls-files)。
